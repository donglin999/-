## 验证

- 自动通关：从新开局跑到进入培养模式，原版与 Godot 都是 299 句对白和选项，逐句一致；剧本节点顺序也一致。
- 对照截图：17 组，见 `docs/review/README.md`。地图与对白的平均差约为 1.4–6.9（压缩底数约 3–4）；菜单为 4.3–10.3；人物交互为 5.2–9.8；战斗为 5.0；培养模式为 6.3。
- 性能：每帧 0.75–1.0ms（原版的帧耗与 Godot 口径不同，不直接比，见第四轮）。点击寻路的中位耗时从 227ms 降到 14ms。
- 加载：Web 首屏只等 21.4MB 主包，原版要等约 50MB、550 张图。其余分包在后台下载，并带构建版本号。
- 实测运行：在内置浏览器里跑 Web 版，控制台无报错；macOS 版解压后可直接运行，有截图为证。

## 第三轮（同日，用户要求“完成还差的地方”）

- 交锋辉光：照原版先叠加画进 1/4 分辨率的离屏层（`fx_layer.gd` 的 SubViewport），贴回时做 blur(8px)（`shaders/fx_glow_blur.gdshader`，按镜头缩放折算）。
- 宋体：引擎的系统字体只取 .ttc 集合里的第一个字重（Songti.ttc 第一个是“黑”）。现在按 PostScript 名从集合里取出浏览器会用的那个字重（宋体常规／粗、楷体常规／粗），存到用户目录 `fontcache/` 下次直接载入（四个合计约 16ms）；不打进安装包，Web 和没有这些字体的系统仍用 Noto。楷体粗体也从加粗模拟换成真粗体。
- 小数字号：引擎字号只能取整数，现在按向上取整的字号排字，再整体缩到原版大小。自绘文字用 `Paint.draw_text`／`Paint.text_w`；容器里的标签套 `Paint.frac`（缩放盒把缩后的尺寸报给父容器）；对白正文（20.5／18.5px）整块缩放。覆盖偷窃、易物、赠礼、人物查看页、比试规则和对白框。
- 交锋节奏：上一轮写的“多播两句喊话”是误判。两边都以第一句喊话为零点、逐步打印时刻（Godot `--clash-timeline`、原版 `tools/clash_timeline_web.cjs`），十二个节点相差不到 0.25 秒。真正的原因是连拍在主线程编码 PNG，每张卡 0.2 秒以上，拖慢了战斗时钟。改成后台线程编码后，十帧招式横幅一一对上。
- 新工具：`-- --checkall`（配 `--headless`）在游戏里逐个载入全部脚本和着色器做编译检查。之前用的 `--import` 查不出脚本错误，本机也没有 `timeout` 命令。

## 第五轮（11-04，用户要求修交锋节奏快 1.8%）

- 逐次记录两边每个战斗等待的实际耗时，查明两边的等待逻辑本来就一致。
  - 原版浏览器 60 帧下，每次等待多等 3–30ms，常见约 10ms。
  - Godot 无头测试时不限帧，约 144 帧，每次只多等 1–5ms，累计成“快 1.8%”。
  - 实际游玩是 60 帧，这个差异不存在。
- `clash.gd` 的 `--clash-timeline` 改为按 60 帧测。
  - Godot 三次：17761–17813ms；
  - 原版三次：17761–17908ms。
  - 结果落在原版自身的波动内。
- 游戏代码的等待逻辑没改。
