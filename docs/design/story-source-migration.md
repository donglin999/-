# 剧情与设定管理迁移方案（设定圣经 + ink 剧本）

状态：现行　最后核对：2026-10-19（原记：**2026-10-18 用户确认；第 1 期试点已完成，待用户审读剧本**（记录见 `xiaojianghu-legacy-prologue/docs/updates/2026-10-18-ink-pilot.md`）（“写进方案，然后开始做试点”）。试点为序章“进村第一夜”（`P-03`，药棚吃饭、换衣、安排住处）。）

用户原话：“我感觉现在的设定和剧情和台词管理都有点太混乱了，我感觉更需要一个类似小说的管理方法去管理了。”

## 0. 要解决的问题

| 内容 | 现在在哪 | 问题 |
| --- | --- | --- |
| 设定（人物、门派、年龄、地点、时间线） | `docs/design` 下几十份 md、`story-atlas.json`、人物卡 json、`cast.md` | 同一个人的信息分在多处，靠 `consistency-check` 事后去查冲突 |
| 剧情结构（部分、场景、触发条件） | 全流程稿、各章 md、`story-scripts.md`、游戏代码里的 `advanceEvents` | 文档里的顺序和游戏实际顺序要人工对 |
| 台词 | 实际演出的台词写在 `xiaojianghu-legacy-prologue/js/qihe-*.js`、`prologue-*.js` 等代码里；文档库另有 `docs/design/scripts/*.json` | 两份互相对不上；改台词要改代码；`story_lint` 要靠导出脚本从 JS 里把台词抠出来 |

行业做法见第 1 节。核心原则只有一条：**单一来源**。设定只在一个地方写，台词也只在一个地方写；游戏数据、总表、检查报告都从那里生成，生成物不手改。

## 1. 参考：行业里怎么分层

| 层 | 管什么 | 成熟方案 |
| --- | --- | --- |
| 设定圣经（Story Bible） | 人物、地点、门派、物品、时间线、规则 | 小说界：Scrivener、World Anvil、Campfire、Obsidian；游戏界：Notion 或 Confluence 维基 |
| 剧情结构 | 部分、章节、场景、分支与触发 | Scrivener 卡片墙；RPG 行业：articy:draft、Arcweave |
| 台词剧本 | 逐句台词、说话人、表情、选项、变量 | ink（inkle）、Yarn Spinner、Fountain；国内常见的是 Excel 台词表加自研导入 |

**选择**：全部用纯文本，放进 git。原因是本作的内容大多由 AI 起草和修改，纯文本最好读写、可比对、可自动检查。articy:draft 虽然成熟，但要付费、主要跑在 Windows 上，文件格式不便直接读写，所以不用。

- 设定圣经：**Obsidian**。文档库本身就是 markdown，直接当作 Obsidian 库打开，不用迁移。
- 台词剧本：**ink**。纯文本，读起来接近小说原稿，支持选项、分支、条件和变量。官方提供网页运行库 `inkjs`（npm 当前版本 2.4.0，自带编译器，可以在 Node 里编译）。

## 2. 目标结构

### 2.1 设定圣经（文档库 `xiaojianghu/bible/`）

```text
bible/
  人物/  叶蘅.md  萧白.md  周婶.md  陈伯.md  宋先生（裴嵩）.md …
  地点/  栖河村.md  栖河·药棚.md  栖河·北坡.md  归云谷.md …
  门派/  正道盟.md  归烬堂.md  巡江司.md …
  物品/  青绫行衣.md  乌木算珠.md …
  时间线.md
  规则/  称呼与口吻.md  时间方案.md …
```

每页开头是结构化字段（Obsidian 的 Properties），正文写描述，页面之间用 `[[叶蘅]]` 链接。例：

```markdown
---
类型: 人物
姓名: 周婶
别称: [阿蘅的周婶]
年龄: 约 50（开始部分）
所属: 栖河村
住处: "[[栖河·药棚]]"
首次登场: P-03-02
口吻: 热心唠叨，话里带活计，不说大道理
立绘: 无（对话用小头像 c_opening_aunt）
状态: 开始部分末尾随村民撤往邻村
---
周婶在村中药棚帮忙，叶蘅从小叫她“周婶”……
```

- `story-atlas.json` 改由脚本从 `bible/` 生成，不再手写；`consistency-check` 读 `bible/`。
- 装 Dataview 插件后，可以直接在 Obsidian 里出“开始部分登场人物”“某年发生的事”这类表。
- 现有 `docs/design` 里的设计文档不搬，只把其中的设定事实（年龄、所属、身世等）收进 `bible/` 对应页，原文改成链接过去。

### 2.2 剧本（栖河试玩版 `xiaojianghu-legacy-prologue/story/`）

剧本放在运行它的游戏工作区里，编译产物直接给游戏用。文档库只链接，不另存一份。

```text
story/
  01-开始/  序章-后山.ink  序章-递水.ink  序章-进村第一夜.ink  第一夜-跑腿.ink …
  02-培养/  …
  03-游历/  …
  04-终局/  …
  _共用/    externals.ink（声明游戏函数）  speakers.json（说话人与立绘对照，由 bible 生成）
```

- 一场戏一个文件，文件里一个 knot（`=== qihe_lodging ===`）。
- 按“开始、培养、游历、终局”四部分分目录，不出现“第几章”。

### 2.3 生成物（不手改）

| 生成物 | 来源 | 用途 |
| --- | --- | --- |
| `js/story-data/<场景>.json` | `story/**/*.ink` | 游戏运行时读取 |
| `docs/story-lines.csv`（或总表网页） | 同上 | 逐句总表：编号、场景、说话人、表情、台词、配音文件，供审读与查找 |
| `story_lint` 报告 | 同上 | 剧情检查直接读剧本，不再从 JS 抠台词 |
| `story-atlas.json` | `bible/` | 兼容现有检查脚本 |

## 3. ink 写法约定

| 内容 | 写法 | 说明 |
| --- | --- | --- |
| 台词 | `周婶：阿蘅，今天回来晚了。 #id:P-03-02` | 全角冒号前是说话人；每句必须带固定编号 |
| 表情 | `叶蘅：…… #id:P-02-01 #mood:worry` | 只在情绪转折处写，与现有 `c_xx:mood` 对应 |
| 心里话 | `萧白：（嗓子干得跟砂纸一样……）谢、谢谢。 #id:P-01-10` | 和现在一样，写在括号里 |
| 时间地点字幕 | `【第二日傍晚 · 装卸路】 #id:C1-M-00` | 无说话人，显示成字幕 |
| 选项 | `* [“我先四处转转。”] -> wander` | 选项前的最后一句台词，就是选择框里的提问 |
| 条件 | `{ not flag("prologue.arrival.borrowed"): … }` | 读游戏存档里的标记，不在 ink 里另存一份 |
| 演出与存档动作 | `~ go_scene("prologue_clinic_interior", "entry_front")` | 换场、淡入淡出、存档点、提示、给物品，都调游戏已有函数（EXTERNAL） |
| 同场人物 | 场景开头 `#cast:叶蘅,周婶,陈伯` | 交给现有的 `DialogueStage` 安排立绘站位 |

**游戏函数（EXTERNAL）首批清单**：`go_scene(场景, 锚点)`、`fade()`、`checkpoint()`、`toast(文字)`、`flag(路径)`、`set_flag(路径, 值)`、`give(物品, 数量)`、`mark(编号)`。每个函数都是现有 JS 函数的一层薄包装，演出效果不变。

## 4. 试点：进村第一夜

### 4.1 现在的写法（`js/prologue-arrival.js` 第 32～46 行）

台词写在一个数组 `lodgingLines` 里，换衣服的淡出、存档、换装、提示都和台词混在同一个函数中。改一句台词要在 JS 字符串里找。

### 4.2 改写成 ink（`story/01-开始/序章-进村第一夜.ink`）

```ink
// 序章 · 进村第一夜（P-03）
// 地点：[[栖河·药棚]]　在场：叶蘅、周婶、陈伯、萧白
// 戏眼：一个来历不明的外乡人被村里收下；住处定在陈伯家空客房；“明天帮您干点活”为跑腿作铺垫

=== qihe_lodging ===
#cast:叶蘅,周婶,陈伯
~ go_scene("prologue_clinic_interior", "entry_front")
~ clinic_stage()

{ not flag("prologue.arrival.borrowed"):
    周婶：阿蘅，今天回来晚了。 #id:P-03-02
    叶蘅：山上碰见个人，头晕得厉害。能让他歇一晚吗？ #id:P-03-03
    萧白：给您添麻烦了。我叫萧白。 #id:P-03-04
    周婶：先坐，杵在门口风大。陈伯，你家那间空客房还空着吧？ #id:P-03-05
    陈伯：空着。就堆了两捆绳，我回去搬开。 #id:P-03-06
    叶蘅：手伸过来我看看。……擦破点皮，不碍事。 #id:P-03-07
    叶蘅：先歇着。要是还难受，叫我。 #id:P-03-08
    周婶：衣服都蹭脏了。我找一身，先凑合穿。 #id:P-03-09
    萧白：我没有这里的钱。 #id:P-03-10
    周婶：一碗饭、一晚榻，用不着算。袖子提起来，别扫着药盘。 #id:P-03-11
    ~ mark("P-03-12")
    ~ change_into_village_clothes()
    萧白：（换上这身粗布衣裳，倒真像个村里人了。原来的衣服和手机，先包起来吧。） #id:P-03-12-result
}

周婶：这两天村里来的生人多，客店都住满了。夜里出门当心，别往车堆里钻。 #id:P-03-guests
周婶：衣裳换好了？快坐，饭还热着。 #id:P-03-13
萧白：谢谢周婶。明天我帮您干点活。 #id:P-03-14
周婶：明天的活明天说。粥放凉了，那才叫白忙。 #id:P-03-15
叶蘅：你今晚住陈伯家那间空客房。我收完药就回家，有事喊一声。 #id:P-03-16

~ set_flag("prologue.arrival.stage", "done")
~ checkpoint()
~ toast("可以在附近走走，或经邀请去叶家帮叶蘅收药箱。")
-> END
```

这场戏没有选项。选项的写法用递水那场戏验证，作为试点的补充样例：

    -> origin_a

### 4.3 游戏这边怎么接

新增 `js/story-runtime.js`，只加载 inkjs 的运行库，不带编译器。流程如下：

1. `StoryRuntime.play('qihe_lodging')` 读取 `js/story-data/序章-进村第一夜.json`。
2. 循环取下一句：
   - 按全角冒号拆出说话人；
   - 从标签里取 `id`、`mood`；
   - 调现有的 `line(id, 说话人, 台词)`，配音和行记照常按编号走。
3. 遇到选项时，把选项前那句当提问，调现有的 `choose()`，再把玩家选的序号交回 ink。
4. EXTERNAL 绑到现有函数，例如 `change_into_village_clothes` 就是现在 `fade(...)` 里那几行（`borrowed=true`、换装、`release`、`checkpoint`）。
5. `lodging()` 只剩一行：`await StoryRuntime.play('qihe_lodging')`。

立绘、对话框、换场、存档、战斗等演出代码一律不动，只把“台词从哪来”换掉。存档仍只在场景边界和 `checkpoint()` 处保存，不保存 ink 的中间状态，与现在的行为一致。

### 4.4 构建与检查

`tools_story/build_ink.cjs` 用 Node 版 inkjs 编译器，在 `scripts/build-pages.cjs` 之前运行。它负责：

- 编译全部 `.ink`，输出 `js/story-data/*.json`；有语法错误就停止构建。
- 检查并报错：
  - 编号重复或缺失；
  - 说话人不在 `speakers.json`（即 bible 里没有这个人）；
  - 表情不在该人物的表情表里；
  - 调用了未声明的游戏函数。
- 导出逐句总表 `docs/story-lines.csv`。
- `story_lint` 改为直接读 `.ink`，老的“从 JS 导出台词”只给尚未迁移的场景用。

### 4.5 试点验收

1. 进村这场戏的台词顺序、编号与现在完全一致（逐句比对导出表与旧数组）。
2. `verify_prologue` 7 项全部通过；`verify_startup`、`verify_chapter` 不变差。
3. 浏览器从头玩到进村吃完饭：立绘、换装淡出、存档、提示都和现在一样，控制台无报错。
4. 总表能导出，`story_lint` 能直接读这场戏。
5. 你通读一遍 `.ink` 文件，确认这种写法读起来顺手，再决定全面迁移。

## 5. 全面迁移的分期

每期只搬运、不改台词，先保证游戏表现完全不变，测试通过后再进行下一期。改台词另起一轮。

| 期 | 范围 | 规模（约） | 说明 |
| --- | --- | --- | --- |
| 0 | 建立 `bible/`：先收开始部分登场的人物、地点、门派；生成 `story-atlas.json` 与 `speakers.json` | 30 页 | 几乎零风险，可以与试点并行 |
| 1 | 试点：进村第一夜＋递水选项样例 | 20 句 | 本文第 4 节 |
| 2 | 开始部分其余：后山、递水、第一夜跑腿、叶家收药箱 | 约 200 句 | `prologue-*.js`、`qihe-map-trial.js`、`qihe-prologue-actions.js` |
| 3 | 风起栖河主体：主线步骤、三方代表、跑腿支线、宋先生、起火与撤离、交锋喊话 | 约 400 句 | `qihe-chapter.js`、`qihe-representatives.js`、`qihe-outsiders.js`、`qihe-faction-clash-data.js` 等；拼接字符串、按状态过滤台词这类写法要改成 ink 的条件和变量 |
| 4 | 培养部分（归云谷三年） | 量最大，另行估算 | `qh-mode-cultivation-*.js`；有自己的剧情状态机，接法单独设计 |
| 5 | 游历、终局 | 新写 | 新内容直接用 ink 写，不再进 JS |

迁移期间，一场戏要么整场在 ink 里，要么整场在 JS 里，不允许两边各有一半。构建检查会列出“已迁移/未迁移”清单。

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| JS 里有拼接出来的台词（如 `'找'+人名+'聊聊'`） | 用 ink 变量或 EXTERNAL 取值；搬运时逐条列出 |
| 按存档状态过滤或插入台词（如三方那场戏的 `filter`、`flatMap`） | 改写成 ink 条件块，验收时逐分支比对 |
| 配音、行记、测试按编号引用台词 | 编号不变；构建检查保证编号唯一且齐全 |
| inkjs 运行库增加加载体积 | 只带运行库、不带编译器；试点时实测体积与首屏影响 |
| 两套写法并存期较长 | 分期推进，每期结束列出剩余清单；新内容只准用 ink |

## 7. 已定事项

用户说“写进方案，然后开始做试点”，按以下默认执行：

1. 剧本放在栖河试玩版的 `story/`，设定圣经放在文档库的 `bible/`。
2. 设定圣经是普通 markdown，用 Obsidian 打开最方便，但不装也能用任何编辑器改。
3. 培养部分（第 4 期）等前三期稳定后再定。
4. 先做第 0 期起步（试点用到的人物与定稿事实）和第 1 期试点。

## 8. 防止新内容推翻旧内容

用户提出：“后面还要考虑一些选择对后续产生影响的问题，需要考虑 AI 在生成新内容的时候不会去推翻旧的内容。”

第 2、3 节的结构只解决“东西放在哪、格式对不对”，解决不了语义矛盾（例如新写的戏让叶父露面）和选择后果断线。为此再加四道机制：

### 8.1 定稿事实表（`bible/定稿事实.md`）

- 把已经定死的事逐条登记。每条包括：编号（如 `F-0001`）、内容、生效时点（从哪场戏或哪一部分起成立）、知情人、来源、是否锁定。
  - 例：`F-0003 叶家没有武谱、玉匣、药样，只有六只旧药罐（对证结论）；生效：风起栖河对证后；锁定`。
- 锁定的条目，只有用户同意才能改。改的时候要写清理由和影响到哪些戏。
- AI 写新内容前，由脚本按这场戏的人物、地点、时点，自动挑出相关事实作为写作材料。写完后，再由独立审读对照这些事实挑冲突。

### 8.2 选择后果登记表（`story/_共用/flags.json`）

- ink 里每个用到的存档标记都要登记：名字、类型与可能取值、在哪些戏里设置、在哪些戏里读取、代表什么。
- 构建时自动报错：
  - 用了没登记的标记；
  - 登记了没人设置，或设置了没人读取（“断线”）；
  - 设置的取值不在登记范围；
  - 按四部分的先后，在设置之前就去读取。

### 8.3 路线遍历

- 构建时，程序按登记表里每个标记的可能取值，把每场戏的各个选项组合都跑一遍。确认每条路线都能走到结尾，没有死路，也没有调用未声明的游戏函数。
- 导出每条路线的完整台词（`docs/story-routes/<场景>.md`），供人工和审读通读。

### 8.4 改旧内容要用户批准

- 用户审过的剧本文件和锁定事实，登记在 `story/_共用/approved.json`，按文件记录内容指纹。
- 新内容默认只能新增文件。构建发现已批准的文件被改动时，列出改了哪几句，并停止构建；用户确认后，用 `node tools_story/build_ink.cjs --approve <文件>` 更新指纹。
- 这样即使 AI 判断失误，也不能悄悄改掉旧内容，只能把冲突摆到用户面前。

### 8.5 独立审读

写新戏时，另开一个子代理，只给它新稿、相关锁定事实和前后剧情，专门挑“与已定内容冲突”“选择后果没接上”的地方。这与 `story-writing.md` 的审读步骤是同一做法，只是多了事实表作依据。

**边界**：以上几道能拦住绝大多数推翻和断线。但语义层的审读最终靠模型判断，所以 8.4 的人工闸门最关键。

### 8.6 落地顺序
