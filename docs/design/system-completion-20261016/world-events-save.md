## 1 事实由谁保存

| 数据 | 权威位置及责任 | 其他模块怎样使用 |
|---|---|---|
| 已经历剧情 | 当前事件负责模块，例如培养facts、preHangao、qiheChapter | 通过事实适配器读取，不再另存一份“全部完成”布尔值 |
| 人物招募、在队与位置 | 人物生命周期合同；既有mates/party/qiheRoutes按现行适配 | 图鉴、地图、教学菜单读取同一快照 |
| 城市阶段与服务 | S.town[townId]的剧情时间点、城市状态与店铺数据 | 地图与商店共同读取，不能一处关店另一处继续卖货 |
| 实际物品和货币 | 正式S.bag与S.silver；装备归属按现行菜单模型 | 原型S.inv不能整体复制进正式存档 |
| 共享历练 | 既有world.jianghuInsight | 发放与消费继续走现有凭据，不让事件再发一次 |
| 已听传闻与核验 | 来源记录及验证事件；参见第5节 | 行记投影成heard/true/false，不将传闻自动当证据 |
| 动作事务 | 本提案新增world.actionTransactions命名空间 | 只记录执行与结算凭据，不取代上述事实 |

每个适配器必须声明读取范围、写入负责模块、旧ID映射和迁移版本。首次没有数据表示“未知/尚未发生”，不根据好感、人物等级或当前所在地图猜测历史。

## 2 一次行动的完整过程

事务状态：`prepared → executing → settled`；用户取消发生于扣款前；技术错误进入`recoverable_error`，能继续或回滚。剧情内正常失败是结果分支，不能写成程序错误。

1. **准备**：以当前存档版本检查事件窗口、前置、参与者、物品归属、体力/货币和排他承诺；给出费用、当前可知后果和确认内容。
2. **执行前提交**：在副本生成唯一事务ID、事件定义版本、随机种子、输入快照和待结算结果；扣一次成本并持久化成功后才切换演出。保存失败仍留原状态，不显示已开始。
3. **演出**：对话和战斗读取同一事务；刷新恢复原句与选项状态，不能重抽结果。事件内部的战斗不另扣同一笔培养体力。战斗子事务的技术回滚回到该次战斗开始快照（已经含父事件费用）；只由父事件整体取消恢复来一次退还父成本，禁止子事务和父事务各退一次。
4. **结算**：先在副本计算一次性事实、物品、关系、城市变化、历练凭据与后续邀请；整体写入成功才替换运行状态并展示结果。已开始而最终结算保存失败时保留executing及costReceipt，不重新扣费、不提前授予；同事务重试或明确父事件整体回滚。
5. **重复请求**：相同事务ID返回已结算的回执；同一一次性事件即使换事务ID也不得再领奖。可重复活动还必须检查当前剧情时间点/培养期的配额。
6. **切换场景**：结果已落盘后，再切地图与人物表现；新场景暂时加载失败不撤销已结算事件，而提供重新加载。

建议最小字段：`id,eventId,eventVersion,status,startedAtClock,inputHash,participants,selectedBranch,costReceipt,resultSeed,effectReceipt,recoveryCursor`。具体存档字段是实现提案，不宣称已存在。

## 3 世界变化与冲突处理

事件效果按责任分组：人物位置/同行状态、服务资格、组织权限、物件、任务、传闻、后续对白。每项写`target,operation,value,sourceEvent,scope,expiresBy,reversible`，并指向负责模块。

优先级只决定**同一个人如何呈现**，不能用于吞掉冲突的已接受任务：

| 场景 | 处理 |
|---|---|
| 剧情正在接管同伴 | 同一实体交给演出控制，暂停队尾跟随；演出结束释放，不复制一个人 |
| 已登记远行/公务，但玩家要邀请 | 禁用邀请并说明可会面窗口；不因关系高绕过职责 |
| 同伴已在队，城市数据仍有静态NPC | 保留其服务入口的逻辑引用，但只显示在队实体；职责要求固定地点时必须先完成离队/驻点事务 |
| 同一时点两个不可兼容预订 | 开始前拒绝第二个或给出明确改约选择；无告知不取消先前承诺 |
| 店铺临时关闭，存在未交任务 | 事件数据必须指定接替人、等待恢复或替代交付位置；没有方案则不能采用闭店结果 |
| 重大事件改变城市 | 用有限的剧情阶段状态更新街区、人物和货架；不启动全城实时模拟 |

事实冲突先按同一事件定义版本与现行确认决定解决；无法找到权威时阻止采用该新增事件并列为待决，不让“最新写入者覆盖”成为故事规则。

## 4 联合日程与资源验证

既有日程检查保留。新增验证读取实际培养公式和城市配额，检查完整目标组合，不把“每条线单独可达”当成同时可达。

每份路线证据必须保存：初始存档摘要、版本、目标组、每步时点/人物/前置、消耗、收益、剩余资源、关系瓶颈、教学资格、关键物件和最终目标。

首组应至少覆盖：

- 必达主线＋剑路＋叶蘅往来＋一条生活学习；拳路用同等投入另验。
- 必达主线＋两位人物往来＋均衡训练，含一次整月历练。
- 普通低培养路线：不要求上限属性或随机稀有物，必要失败有允许的补做。
- 主动错过一条可选约定：产生对应错过事实与后续入口，不能把整条主线关闭。
- 同伴暂离/驻外、材料不足、快进跨窗口、存档升级时的反例。

149自由期/1788体力是当前运行预算；141自由期/1692体力属于九段主线预留范围。求解输入必须注明采用哪一范围，禁止混合两套上限。求解超限输出`unknown`，缺少数据输出`incomplete`；二者都不算通过。

## 5 传闻 证据和人物看法

最小条目包含`id,claim,sourcePerson,sourceEvent,observedAt,kind,confidence,verificationRefs,visibility`。

- `kind=rumor`：有人这么说。记录来源和听到时间，不能据此确认客观事实。
- `kind=observation`：玩家/在场同伴亲见；说明观察范围，不把有限细节扩成全案结论。
- `kind=verified`：满足该事实负责页要求的核验事件；必须能追溯依据。
- `kind=opinion`：人物的判断或立场，可以与别人的意见相反，不应当成世界状态冲突。
- 假传闻保留“曾听过、后已核伪”的经过，不删除历史。最新核验更新展示状态，原来源仍可查。

现有行记继续只列已承办/已完成的真实事项。新增信息在当前目标下展示“知道什么、还欠什么、哪里能核对”；不列尚未认识的人物，不展示未选择分支的结局。追踪只改变HUD关注对象，不接任务、不传送、不付钱、不领奖。

离开一个剧情时间点前，从同一任务数据生成截止提醒：仅列玩家已知道且将失去的机会；必要补路仍指向已知人物或明确来信，不用全知攻略直接给出隐藏答案。

## 6 存档备份与升级

沿用当前自动旅程、不可被自动保存覆盖的手动副本、回收站和评审隔离。新增本地导出/导入是提案；云同步与跨设备账户体系后排。

导出包：格式ID、存档版本、运行身份、导出时间、旅程名称、负载摘要、payload和校验值。校验值只能发现意外损坏，不当作防作弊签名。导入只解析JSON，不执行脚本，不信任里面的路径或URL。

导入顺序：验证格式/大小/校验 → 检查所需版本 → 在副本迁移 → 展示章节阶段/地点/人物/资产摘要及警告 → 创建新旅程 → 持久化成功后才允许继续。默认不覆盖当前或唯一原件；失败留原文件与原旅程。输入大小上限随正式存档压力样例确定并列入发布清单，不用无限制读取。

迁移原则：

1. 追加新字段给中性默认，不把已关闭/未发生事件补成成功。
2. 旧事件有活动快照则按该快照完成一次，再使用新定义；无法兼容时退回已保存的开始前状态并给清楚提示。
3. 改期只迁移未开始邀请，说明新窗口；已结算结果不重发。
4. 改名通过稳定ID别名映射；未知物品/状态保留为不可用记录，不能静默删除财产或使其产生效果。
5. 减少队位保留正式资格与物品，不随机弃人；角色迁居与关键证物移交同一事务完成。
6. 版本过新拒绝载入但保留原件；版本过旧且无已验证路径时说明需升级，不假装转换成功。

发布验收至少包括：保存空间不足、导入损坏、重复导入、进行中对话/战斗、事件改期、未知物品、手动副本续玩、回收站恢复与评审档误导入。
