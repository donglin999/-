# 场景容器与探索获取规范

日期：2026-09-30。状态：**用户已确认方案一、所有可获取点使用淡蓝闪烁、当前每张可探索地图有逻辑地配置容器；下列具体位置、奖励与数值是实施设计。**当前本机已接入 20 个点、领取和存档；测试与发布状态见[实现记录](../containers.md)。

适用：羊太傅庙、庙外、襄阳南门、街市、偏巷、东津渡、渡船、东岸芦苇荡、黑风寨寨门、山洞，共 10 张现有探索地图。大地图只作地点导航，不放可拾取容器。未来地图按本规范补登记后才能制作。

## 1. 体验目标

玩家能从真实物件与淡蓝闪烁发现可打开的容器，走近打开并获得合乎地方用途的物资；获取后物件可见地变空或打开，读档也不重复发放。容器服务场景生活、仓储和据点用途，不随机撒点，不把草地中的发光坐标当宝箱。

本期只做宝箱、普通货箱、衣柜、木桶及类似实体容器；草药、矿石和自由采集属于另一个系统，不顺带生成。首期固定奖励、一次领取；不设随机品质、地图刷新、钥匙抽奖、长按进度或负重限制。

重要原则：**放哪里、谁拥有、装什么、为何能拿、价值多少**必须同时明确。开箱不自动装备、不自动使用、不教授武学；物品进入行囊后按现有规则处理。

## 6. 淡蓝闪烁提示

用户确认：**每个当前可交互获取的容器都有淡蓝色闪烁提示。**它表示“现在还有东西可拿”，与任务感叹号、挖掘提示和装备品阶无关。

- 色彩起点：淡蓝 `#9EDFFF`，中心少量 `#D7F4FF`；不使用饱和霓虹蓝。颜色为效果参数，不烘焙进家具。
- 一个主光点在箱扣、柜门把手或桶盖边缘，附 1–2 个小闪点；周期约 1.8–2.4 秒，各点用稳定 ID 偏移相位，避免全地图同步闪。
- 用户已批准强化版 GIF：主星芒约 24 像素跨度、辅星约 8–12 像素，局部光晕半径约 34 像素（预览画布尺度）；实际游戏按画布缩放保持相近观感。局部淡蓝光缓慢明灭，不画大光柱、整圈法阵或整屏白光。预览原文件为 `review/container-hint/blue-sparkle-large-fixed.gif`；废弃含空白帧的旧版。
- 所有可获取点在镜头内可见时都提示；白天应能辨认、夜景不刺眼。提示由容器本身随场景遮挡，不能隔着屋檐/墙透出引导玩家点空气。
- 鼠标悬停额外给轻描边/淡蓝轮廓和“名称 · 打开/搜寻”小标签；光点无需靠近才出现，完整名称只在悬停/近距离出现。
- 未开放、已领取、纯查看、不可擅取的物件均不闪蓝。尚不可取的物件可悬停读到“有人看守”等具体原因，不用灰色闪烁伪装成可拿。
- 第一次领取完成后同帧熄灭蓝闪；已搜过仍可查看状态，提示“已取空”。不留下闪点但点开没有东西。
- 暂停、菜单和页面失焦遵循现有渲染节奏；开启减少动态效果时改为稳定淡蓝小光点，语义保持一致。

## 7. 交互与领取流程

1. 鼠标对准真实容器可见轮廓；点击远处容器，规划到登记的可达互动站位。近处按 E/空格也能获取，不新增必须鼠标操作的入口。
2. 到达后再次核查当前地图、领取状态、开放条件、距离和合法站位。角色隔墙或站在不可达位置不能远程开箱。
3. 普通无锁容器播放 0.25–0.45 秒开盖/开门反馈和木质轻响；将短动作与玩家移动解耦，不弹强制确认、不长时间置 busy。主角输入不因奖励提示锁住。
4. 领取一次性提交：数量、银两和已领取状态同时更新并保存，随后通知界面。连点、键盘重复、切图都不能再次发奖励。
5. 在画面侧边显示物品图标、名称和数量；多奖励按图标列表排布并自动消退。普通箱不弹模态对话，奖励不自动使用/装备。
6. 容器切换为开/空状态、移除蓝闪，保留符合环境的实体。之后再次交互只作简短非阻塞“已取空”提示。

背包已拥有同物品时叠加，不覆盖现有数量。不含未实现的容量上限。核心存档读写失败时给明确提示，不能宣称领取已安全保存；故障处理要避免只写奖励或只写领取旗标。长文本剧情和奖励反馈分别走现有对话与非阻塞提示入口。

## 8. 空间和碰撞规范

每点登记三种空间：物件绘制锚点、实体占地、互动落脚点。互动点不等于物件中心；木箱、衣柜和木桶均为实物，玩家在其边缘站立，不踩进柜门或桶里。

- 家具靠用途对应的墙/棚/货区；正面可接近，开门方向有余地。不在出口触发带、窄桥中央、主线战场、NPC 固定站位或进场动画线路上摆容器。
- 衣柜只在实际可见的室内或干燥洞内放；未开放住宅内景不为了凑衣柜点穿墙进入。
- 漂流物放可达岸上，不能仅让鼠标命中却无法走近。
- 地图生成器先排新单体，再从实物足迹生成 mask；点击寻路以真实碰撞为准。不要为防止点击多画一圈空气墙。
- 每张图 1–3 点，重要用途区域集中、路边净空保留；不按网格均匀分布，不在所有屏幕角落硬塞箱子。
- 语义位置固定；若需调坐标绕开障碍，只能在所属功能区内微调并记录，不把药箱挪到河岸或衣柜挪到野外。

| 客宿旧衣柜 | 高柜、粗木门、挂衣；不做宫廷雕花 | 关门、门开有衣、门开取空 |
| 洞中矮衣柜 | 潮旧但可用，矮柜与粗衣，不同于宝箱 | 同上 |
| 干粮桶 | 有盖、干燥、布包，区别敞口水桶 | 盖闭、盖开有物、盖开取空 |
| 酒桶 | 木箍、塞栓/桶口，复用现有山寨酒桶形制 | 未搜、已搜；少量酒提取，不画整桶凭空消失 |
| 弃箱/漂来木匣 | 破盖板、磨损或水痕；散钱藏于夹缝 | 未搜、盖板移开取空 |
| 墙根藏匣 | 小尺寸、朴素铁扣，符合泼皮藏钱 | 闭合、打开、空 |

每件制作记录：`assetId、用途、所属点、现有参考、源尺寸、运行尺寸、投影、地面锚点、占地、开盖方向、三状态、透明背景、评审路径`。没有确定运行尺寸和物件参考，不能先批量生成。

生成提示词必须包含：南宋武侠场景、现有地图三分之四俯视角、对应木材/铁箍/布料、使用与磨损原因、统一脚底锚点、透明背景、单件无环境、所需开/关状态。禁止现代锁具、金色宝光、游戏 UI、蓝色粒子、奖励文字、与用途无关的珠宝。布签文字由代码/人工排版，生成图不要写难辨伪汉字。

三个状态必须保持物体尺寸、投影、主轮廓与落地阴影一致；箱盖/柜门打开可以改变外包围盒，但底座位置不变。不得每个状态重新随机设计家具。先用同一形象参考制作状态，再在实际昼夜地图和角色比例下审稿。仅静态评审合格还不能代替取后切换与遮挡测试。

## 10. 数据与开发接口

建议独立登记容器，不把它伪装为会走动的人物 NPC。可兼容现有 E 键目标选择，但绘制、点击范围、条件与领取由一个容器模型维护。

```js
// 结构草案；实际坐标和代码开放条件须在实施时核定。
{
  id: 'cave_aid', scene: 'cave', kind: 'medicine_chest',
  asset: 'container_medicine',
  visual: {x: 0, y: 0},       // 世界像素，0 是未布置占位，不可据此上线
  approach: {x: 0, y: 0},
  footprint: null,           // 未测量占位；接入前必须补实物占地
  ownership: 'bandit', access: 'after_chief_defeat',
  rewards: {items: {pill: 1}, silver: 0},
  reason: '守寨者备用伤药', value: 20
}
```

- 持久领取记录建议 `S.containers[id] = {claimed: true}`；全局 ID 唯一，跨地图和往返不变。旧档没有该字段视为未领取，不重新发其他剧情奖励。
- 点位与奖励登记一处、素材登记一处；提示状态取自同一开放/领取判断，不在绘制层复制掉落规则。
- 空箱仍保留绘制实例，但从“可领取”目标列表移除；查看入口可保留。存档只保存稳定 ID 与领取状态，不保存图像对象、Promise 或动画计时。
- 新版删点或改奖励不得重置已领取状态。合并点位要有迁移规则；现有 snake/埋酒点只能适配原旗标，不能当作新箱重新补发。
- 初始化校验所有地图 ID、容器 ID、物品 ID、数量、银两和开放入口；不存在或负数量配置明确报错并禁用领取，不静默随便换奖励。
- 当前每点领取由同一入口完成，先检查数据与合法性，再提交奖励和领取状态，再表现音效/动画。奖励已经提交后画面失败不得通过再点补发。

## 11. 验收与后续制作顺序

### 文档与布置

逐个核对 20 个登记 ID、地图数量和价值预算；所有地图至少一个点，每点都有合理归属与取用说明。开放旗标在代码中逐个查实，正义解围/分赃等分支不能一概用“事件结束”放行。

### 本机实机

- 两视口 1280×720、1920×1080：正常游玩机位能发现淡蓝闪点，昼夜可读，悬停名称对应实际物件；屋檐后不能透光提示。
- 逐点从地图入口真实走到，点击寻路与 E 键均能拿取；草地无空气墙，物件不穿模，领取提示不阻止移动。
- 首领存活/败后、东岸未解围/解围、西岸正义/分赃、船上战斗中/战后分别核对开放与蓝闪；已经领取永不再闪。
- 连点与键盘重复只奖励一次；离场、返图、读档、浏览器刷新后状态一致；旧档不丢失原背包或任务旗标。
- 比较取前/取后同机位画面：真正开盖、衣物减少或空桶，而非仅文字提示；地图烘焙旧像素不残留。
- 按正常资源走一轮，检查额外衣物卖钱与补给量，不把评审直达的高等级状态当作平衡依据。

### 制作顺序

1. 确认本篇清单与用途，绑定真实条件，测量锚点/占地并画点位图。
2. 出箱、柜、桶的同尺度参考与状态样张，在地图中合成审稿。
3. 再批量制作状态素材，接入碰撞、提示、获取、存档。
4. 逐点本机实走与分支回归，记录截图、领取差额、错误和未覆盖项。
5. 更新实现状态后再发布；本机实现与线上发布分开记录；生成样张不能当作实机通过证据。

## 12. 本批布置说明

实际位置来自 `js/containers.js` 的固定源图坐标，所有地图使用既有世界倍数 3；新容器由独立运行层绘制并将同一实体占地加入碰撞/寻路，不重画整张地图或随机摆放。现有底图、人物与地图图集保留。衣柜在客宿/草铺储物侧，岸边匣在可走岸上；棚边箱桶放在檐前/侧面可达位置，不能要求穿进尚未开放的屋内。酒桶独立制作酒瓶三状态，不能复用干粮桶的布包内容。


## 13. 容器比例修订（2026-09-30）

用户反馈首批容器过大，要求比人物小。以主角 92 世界像素身高作基准：普通箱桶闭合宽度 42–66 世界像素，闭合高度约 30–51；两类矮衣柜闭合高度约 66 世界像素，开门后外轮廓最大约 78 世界像素。所有容器状态的可见宽高均小于主角身高，不按完整成人高衣柜做压迫性的占地。源图缩放由统一素材构建器控制；碰撞与点击范围取同一元数据同步缩小，不留下旧大占地。船上桶保留原先较小的实际尺寸，避免二次缩小到难以辨认。

淡蓝星芒维持用户批准的提示大小；只缩实体容器，不把物件尺寸和提示亮度混为一个参数。未领取/开盖/取空三状态维持同一底座比例与锚点。
