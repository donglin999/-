# 试玩审查（问题类型清单与流程）

状态：现行　最后核对：2026-11-09

全套自测只回答“能不能跑通”（台词、报错、卡住、和上一版画面比有没有变），不回答“玩起来对不对”。试玩审查补这一块：像玩家一样看画面、读剧情，按下面的**问题类型**逐张查。

由来：2026-11-09 用户试玩开始部分，指出七个具体问题（点“交谈”没反应、叶蘅瞬移、两种任务框一大一小、无用的酒缸、小耗子直接教偷、货郎碍眼且行记里没有、树和石凳重叠），并要求：具体问题不直接写进清单，要提炼成**问题类型**再去审查；看图交给本机命令行的 Claude Code（cc）。七条的整改见 [2026-11-09-playtest-fixes.md](updates/2026-11-09-playtest-fixes.md)。

## 一、问题类型

每一类写明：查什么、由谁查（脚本／看图／读剧本）。新发现的问题先归到已有类型；归不进去才加新类型，并写明由来。

| 编号 | 类型 | 查什么 | 由谁查 |
| --- | --- | --- | --- |
| T1 | 交互没反馈 | 看起来能点、能按的东西（印、标签、按钮、提示里写的动作）点了要有可见结果：台词、提示、面板、换场景。提示出现了就必须能做成；做不成也要说为什么 | 脚本（扫荡“没反馈”）＋看图（像按钮却点不了的元素） |
| T2 | 人物与时空不连续 | 同一时刻一个人只在一处；人从甲地到乙地要有交代（同行、走过去、转场、台词说明）；站位和剧情一致（剧情说他在家，地图上就该在家） | 脚本（扫荡“一人两处”）＋读剧本 |
| T3 | 同类界面不统一 | 同一类元素（任务框、标签、卡片、按钮、题签）的宽度、字号、内边距、底色、边线要一致；同一功能在不同部分用同一套界面 | 看图 |
| T4 | 物件没有理由 | 地图上每个物件要么有用途（交互、剧情、任务），要么有生活上的理由（店门口的货、院里的柴）；只为填空的、和环境无关的删掉 | 看图＋查数据（无交互的大件） |
| T5 | 摆放不合生活逻辑 | 人和物不挡在路中间、门口、必经之路上；摊贩靠路边、货靠墙；朝向、位置像真有人在这里过日子 | 看图 |
| T6 | 素材重叠穿插 | 物件和物件、物件和人、物件和建筑互相压住、穿插、一半埋进另一个里；前后遮挡关系反了；同一张素材里画进了别的东西又和地图上的重复 | 看图 |
| T7 | 素材状态不自然 | “坏了、断了、倒了、空了”这类状态图要合乎常理、和周围画风一致，不生硬、不夸张 | 看图 |
| T8 | 任务没登记 | 接下的事（提示“已接”、答应了帮忙）都要进行记，有当前目标、地点、进度；做完要标完成 | 脚本（“已接”提示与行记对照）＋看图（行记页） |
| T9 | 剧情动机与过渡 | 人物的要求有来由、有铺垫，不开口就念规矩、讲道理；不让玩家无缘无故做坏事；前后句接得上 | 读剧本 |
| T10 | 剧情与玩法脱节 | 剧情里教的、让做的动作，要用游戏里对应的入口完成（教偷就用“窃”、比武就进战斗），不用“谈”一笔带过；台词里不说界面术语，操作提示放在提示条 | 读剧本＋查代码入口 |

## 一点五、江湖菜单扫荡（2026-11-10 起，脚本）

- 脚本：`scripts/tests/menu_sweep.gd`。
- 用法：`godot --headless --path game -- --menu-sweep=<进度点.json> --out=<报告.json>`。全套自测里用第 01、06、09 三个进度点自动跑。
- 做什么：读档后把七个页签逐页打开，有头像列的页对每个结伴的人各做一遍：
  - 每个可点的东西从干净页面点一次；
  - 每个浮签取一次内容；
  - Q、E、Z、C、Esc 各按一次。
- 报什么：
  - 报错；
  - 浮签空；
  - 越界：可见文字一半以上出了画面或被裁掉（滚动区里的不算）。
- 另列“点了没变化”备查：大多是点已选中的页签，要逐条看。2026-11-10 第一次全量跑时，从这里查出设置页的“战斗界面”一项点了没反应。

## 二、流程

1. **采集**：`python3 tools/playtest_review.py capture`：
   - 场景：每个场景按镜头大小铺满整张地图截图，村中日常和第一夜各一套。
   - 界面：菜单各页、墨印菜单、追踪栏。
   - 输出：图在 `build/playtest/<时间>/shots/`，清单在 `shots.json`（每张写场景、镜头位置、进度）。
2. **看图**：`python3 tools/playtest_review.py review`：
   - 把截图分批（每批 4 张）交给本机 cc：`env -i HOME PATH USER TERM=dumb claude -p --model claude-opus-5-5 --allowedTools Read`，提示词里附第一节清单。
   - cc 每批输出 JSON：哪张图、类型编号、位置、问题、轻重。
   - 剧本：`--story <ink 文件…>` 时，把剧本全文交给 cc，按 T2、T9、T10 读。
3. **复核**：主会话逐条看 cc 报的问题和原图。
   - 误报：写明原因，不改。
   - 真问题：按类型归档，修掉，或发评审台请用户定。
   - 汇总：写进 `build/playtest/<时间>/report.md`，再整理进当次更新记录。
4. **什么时候跑**：
   - 改了地图、物件、人物站位、界面、剧情之后，交给用户试玩之前。
   - 全套自测只跑脚本那部分（T1、T2、T8）。看图和读剧本另外跑，大约十几分钟。

## 三、已知误报（复核时直接排除）

- 空地上的闪光：隐藏宝物的提示，设计如此。
- 野地、河边单放的箱子：宝箱（用户定看见就能开，贵重箱只靠位置）。
- 品级角标“丙”在小字号下常被认成“内”。
- 室内场景（客栈、叶家、陈家、山上客院）是整张画的底图，家具摆放问题只能重画；户外场景的道具、宝箱、采集点、人物站位可以改数据（对照 `tools/map_props_view.py` 拼的序号图）。
- 剧情站位：人物在某户门口和人说话这类，先查是不是用户通过的站位（2026-10-31“全场站位”），是就不挪。
- 露天的桌凳、工棚前的工作台：放在自家院里或棚前空地上的，算有生活理由。
- 楼梯、台阶旁的物件：先看楼梯从哪边下来、物件是不是立在地上，cc 常把楼梯方向看反。
- 画在底图或整张素材里的摆放问题，用 `tools/patch_region.py` 局部重画：裁一块、只改一处、只贴回允许改的范围。室内场景另有前景层 `*_fg`（压在人物上面做遮挡），家具也画在里面；改了底图要同步清掉前景层里对应的东西，否则游戏里还看得见（2026-11-09 第四十八轮踩过）。
- 采集工具的坑（已在工具里规避，改工具时别再犯）：
  - 镜头靠挪主角来对准，主角会被放到屋顶、柱头、树冠里，截图时要藏起主角（`hide-player`）。
  - 借截图对比用例时，带按键（keys）的用例不能只取它的场景参数和说明。

## 四、维护

- 用户试玩又指出问题：先归类型；归不进去才加一行新类型，写明由来。不要把具体问题原样抄成一条。
- cc 漏报的，回头看是清单写得不清还是截图没覆盖到，改清单或采集范围。
