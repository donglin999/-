## 当前接话修订：让人物依据已知信息说话

用户指出“那来客的时候，谁去招呼？”像主角提前知道下一条规矩。删除这种为引出设定而预设的问题：萧白只回应已经听到的受伤须告知；由师母主动补充来客奉茶。萧白听到“无论正邪”之后，再问寻仇者是否也奉茶，疑问来自刚听到的内容。

同场自报年龄保留“我十四、十一岁入门”，去掉小豆未经询问便知道萧白年龄的“小三岁”精确比较。二人年龄差仍在人物设定中成立，不要求新相识的人在台词里提前算出。只改当前编辑精简候选，不改历史API响应，不进行API重生成，不将整场候选接入正式游戏。长度仍按原版±15%检查，实际结果见`short-rewrite/length-report.json`。

2026-10-12用户指出少年立绘与同岁设定不符，确认小豆在拜师面初见时14岁。依据[归云谷一家](../../../design/guiyun-household.md)同步：11岁入门、早萧白三年；正式对白与图鉴纠正同岁说法，喂鹅回忆也回到十一岁。立绘和Q版沿用少年形象，不生成成年版。

年龄修订时精简稿改为“你瞧着比我还小……”接自报十四、十一岁入门，当时18句406字；后续接话修订见上节。当前正式稿376字。**仅四句年龄相关纠错进入正式对白，整场MiniMax/编辑重写仍为候选。**

历史`baseline.json`与API提示词/响应保留旧年龄，以免篡改生成证据；新`baseline-current.json`明确记录本次用户授权和源SHA，供当前短稿对比。首轮历史页已标注旧年龄。当前写作要求为`short-rewrite/brief-current.json`，它是更新后的规范，不冒充曾发送的API请求。本轮未调用生文/生图/配音接口。

## 第三轮：保留自由组织，恢复原版篇幅（当前方向）

用户认为第二轮明显过长，确认原版长度合适。本轮仍由 MiniMax-M3 按人设与情境创作，不沿用旧句位；以原版每条可见剧情路径的字符数（含标点）设置 85%—115% 篇幅预算。舞台说明同样计入预算，不允许通过拆碎短句或堆动作扩充篇幅。字数/话轮先核验，超限稿不能冒称已收紧。

实施结果：MiniMax 请求对严格计数执行不稳定，出现推理耗尽、碎句变多、字数不足、称谓和事实偏差。本轮保留七次实际调用记录，停止继续付费反复计数；随后由 Codex 基于 MiniMax 候选与既定剧情做编辑压缩和纠错。**最终短稿署名为“MiniMax 草稿 · 编辑精简”，不是 API 原文**，机器记录 `post_editing=true`、`editor=Codex`。未把人工修订冒充模型生成。

## 第二轮：依人设与剧情自由重写（历史）

用户反馈首轮只是替换词语，要求不再受原句、句数约束。第二轮 API 输入不包含当前台词、上一轮台词、行 ID、句数或原场景接话顺序，只给角色设定、每场剧情起点、必要事实与结束状态。由 MiniMax-M3 自主设计具体动作、话题转折、先后与篇幅。人物年龄、师承关系、消息可信度和功法传承仍需保持；场内小动作可新写，但不凭空增加主线事实、能力或场外角色。

四场题材维持不变。路图事件保留抄图/请教两种玩家选择的意义，分别呈现；其余三场自由编排连续对白。不要把争蛋、数息睡着等原有段子设为必选素材。成稿以整场比较，不强行按旧句位对齐。新对照页提供“当前稿 / 上一轮 MiniMax”作左栏，右栏为独立自由重写；API 成稿与编辑评语分离。首轮记录保留，候选均未接入正式游戏。

参数更正：进一步核对[官方 OpenAI 兼容 API 参数](https://platform.minimax.cn/docs/api-reference/text-openai-api)，`reasoning_effort` 仅对 M3.1-Flash-Preview 生效，之前给 M3 传 medium 不能宣称实际降低了推理档位。本次自由重写第一次请求耗尽 28,000 输出 tokens，未得到剧本，已归档。重新调用仍使用 M3，按文档设 `thinking.type=disabled`、`max_completion_tokens=18000`，直接生成成稿，梗概与创作自由不变；不冒称为 M3 最大推理版本。

## 第一轮设计（保留追溯）

第一轮按用户要求用 MiniMax API 重写同样几段剧情，与当前稿比较。选取「近路之外」「拜师面」「初识心法」「先给她看」，覆盖初见来客、师门日常、传授内功和叶家线索四种情境。当时将采用文本的行 ID、人物、分支、舞台名单及剧情事实固定，仅请求改写台词；这一句数限制已在第二轮取消。

输入从 `../scripts/chapter-two-dialogue.json` 的当前 `text` 字段提取，另附负责文档中的角色关系及每场不可改变的事实。输出逐句对应原 ID，标题卡和鹅叫也保留，因此比较的是同一场、同一句位；分支彼此独立，不把不同条件的对白连读。

模型选择依据：[官方模型列表](https://platform.minimax.cn/docs/guides/text-generation)、[M3 官方页](https://www.minimax.io/models/text/m3)。查阅时公开 API 的旗舰正式型号为 MiniMax-M3；M3.1-Flash-Preview 限 M Plan / MiniMax Code 订阅。先请求 M3；如账户不可用，应记录真实失败，不静默冒用更低型号。

验收：保存无密钥的完整提示词、请求参数、实际返回型号、用量与模型原始成稿；逐句检查 ID 覆盖、发言者、分支和核心剧情事实。候选不由 Codex 润色后再署名 MiniMax；若发现问题，在独立评语列指出。密钥只从现有本地配置读入进程，不写入请求文件、网页、输出日志或 Git。

实现与证据存放于兄弟正式工作区 `review/cultivation-minimax-compare-20261012/`，预览使用既有 8792 服务，不改游戏对白或普通存档。对照页提供逐句并排、整段阅读与意见导出。

## 第一轮完成（历史对照）

[打开四场对照](http://127.0.0.1:8792/review/cultivation-minimax-compare-20261012/)。四场共 63 句，MiniMax-M3 返回 51 句改写、12 句保留（含字幕、鹅叫及自然短句）。右栏与 API 最终成稿完全一致，没有经过 Codex 润色。独立的 `editorial-notes.json` 标明事实检查与仍然别扭的说法，不能把“结构检查通过”当作“文学质量通过”。
